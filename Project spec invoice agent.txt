---------------------------------------------------------------------
1. GOAL
---------------------------------------------------------------------
Build a LIVE, RUNNABLE web app that takes a vendor invoice PDF as input and produces a clear,
reasoned decision as output, with every intermediate step visible.

Decisions (4 statuses):
  APPROVED      all checks pass
  NEEDS_REVIEW  a human must look (soft variance, suspected duplicate, bank change)
  ON_HOLD       information missing; vendor must be asked (drafted email included)
  REJECTED      hard policy failure (blocked vendor, exact duplicate, over-billing)

Grading focus from the brief:
- It actually runs end to end on real PDF inputs (not a mockup).
- UI has a LIVE RUN VIEW (each stage shown as it executes) and a DASHBOARD (history, status, outputs).
- 2-4 non-trivial edge cases handled deliberately.
- Clear explanation of every decision.
- A 5-minute demo video and a live demo in the interview.
- No Zamp or Pace tools. No paid API required.

CORE PRINCIPLE: "LLM reads, code decides, text explains."
The LLM (or offline parser) only EXTRACTS fields. A deterministic Python rule engine makes the decision.
The model never approves a payment.

---------------------------------------------------------------------
2. ASSUMPTIONS (show these on the Settings page in the UI)
---------------------------------------------------------------------
1. Two-way match only (invoice vs PO). Goods receipt / three-way match is a listed next step.
2. Single currency (INR). Amounts printed as "INR".
3. Vendor master and PO ledger live in SQLite, seeded from CSV files.
4. Input is a PDF upload (email ingestion is a stretch goal).
5. Each PO has a "basis": "gross" (tax-inclusive) or "net" (pre-tax). Invoices are compared on the PO's basis.
6. Partial billing against a PO is allowed (invoice may be less than the remaining balance).
7. Policy values live in a table and are shown in the UI: hard_pct=5, dup_window_days=7,
   min_confidence=0.7, vendor_match_min=75. Per-vendor soft tolerance: tolerance_pct and tolerance_abs.
8. All test invoices are synthetic.

7. PIPELINE BLUEPRINT (the live run view shows exactly these stages)
---------------------------------------------------------------------
Stage names (use these strings): ingest, extract, confidence_gate, vendor_check, po_match,
duplicate_check, financial_validation, decision.

Each stage emits "running" then "done" via emit(run_id, stage, state, detail, ms).
Wrap pipeline.run in try/except: on any exception set status FAILED, emit stage "decision" with
{"status":"FAILED", ...} so the UI never hangs.

1) ingest
   - read bytes, compute SHA-256, store file_hash on the run. detail: {"hash": first 12 chars}

2) extract
   - x = extract(path). Returns the schema in section 8. detail: the extracted dict (includes "engine").

3) confidence_gate
   - missing = required fields among [invoice_number, invoice_date, total] that are falsy
   - low = fields in field_confidence with value not None and < min_confidence, among the same required fields
   - if missing or low -> ON_HOLD, codes ["MISSING_FIELDS", "FIELD_<NAME>" ...], drafted vendor email
     listing exactly which fields were unreadable. STOP.

4) vendor_check
   - best fuzzy match of vendor_name against vendors.name using rapidfuzz token_set_ratio (lowercase);
     exact tax_id match forces score 100.
   - if no vendor, score < vendor_match_min, or vendor.status != "approved" -> REJECTED, ["VENDOR_NOT_APPROVED"]. STOP.
   - bank check: if extracted vendor_bank_account exists and differs from vendor.bank_account ->
     NEEDS_REVIEW, ["BANK_DETAILS_CHANGED"], explanation mentions possible payment fraud and phone verification. STOP.

5) po_match
   - if po_reference present and exists in pos -> method "explicit"
   - else candidates = POs of this vendor where (total - billed) >= 0.98 * comparable_amount (see rule below);
     exactly one candidate -> method "inferred"; zero -> "none"; more than one -> "ambiguous"
   - no PO -> ON_HOLD, ["PO_NOT_FOUND"], email asking vendor for the PO number. STOP.

6) duplicate_check (compare against past runs with status APPROVED or NEEDS_REVIEW, any file)
   - exact: same file_hash -> REJECTED, ["DUPLICATE_EXACT"] with the earlier run id. STOP.
   - fuzzy: same vendor_id AND ( normalized invoice number equal
            OR (abs(amount difference) < 1 AND invoice dates within dup_window_days) )
     -> NEEDS_REVIEW, ["DUPLICATE_SUSPECTED"], explanation references the earlier run id. STOP.
   - normalize invoice number: uppercase, remove the word REVISED, remove all non-alphanumerics.

7) financial_validation
   - comparable_amount: if po.basis == "net" use net (subtotal, or total - tax_amount when subtotal missing);
     else use gross (total).
   - remaining = po.total - po.billed
   - over = comparable_amount - remaining
   - if over <= 0 -> ok (partial billing)
   - soft = tolerance_pct% of remaining; if vendor.tolerance_abs > 0 then soft = min(soft, tolerance_abs)
   - if over <= soft -> ok
   - elif over <= hard_pct% of remaining -> NEEDS_REVIEW, ["VARIANCE_SOFT"]
   - else -> REJECTED, ["OVER_BILLING"]
   - detail: {invoice, po_remaining, variance_pct, basis, result}

8) decision
   - APPROVED: reason codes ["VENDOR_OK", "PO_MATCHED_EXPLICIT" or "PO_MATCHED_INFERRED", "WITHIN_TOLERANCE"];
     update pos.billed += comparable_amount; explanation includes remaining PO balance after approval.
   - Save status, reason_codes, explanation, extracted, po_number, amount, vendor_id, email_draft on the run.
   - emit stage "decision" done with {"status","codes","explanation"}.

Explanation text is templated from facts (deterministic). Optional: one Gemini call to rephrase it in plain
English; it must never change the status or codes.

8. EXTRACTION SCHEMA (the dict returned by extract(path))
---------------------------------------------------------------------
{
  "vendor_name", "vendor_tax_id", "vendor_bank_account",
  "invoice_number", "invoice_date" (YYYY-MM-DD), "due_date", "po_reference",
  "currency", "subtotal", "tax_amount", "tax_included_in_line_items", "total",
  "line_items": [{"description","qty","unit_price","amount"}],
  "field_confidence": {"invoice_number","invoice_date","total","po_reference","vendor_name"},
  "document_quality": "clean" | "scanned" | "poor",
  "missing_fields": [],
  "engine": "gemini" | "offline"
}
Rules: unknown fields are null, never guessed. The pipeline recomputes math itself; never trust the model total blindly.

extract(path) logic:
  1. sha256 of file; if USE_CACHE=="1" and cache/<hash>.json exists -> return it.
  2. if GEMINI_API_KEY set: try extract_gemini(path); on success write cache and return; on any exception fall through.
  3. return extract_offline(path).

extract_gemini: google-genai client, model from GEMINI_MODEL, contents = [PDF bytes part (application/pdf), schema prompt],
  config response_mime_type="application/json"; strip ``` fences; json.loads; set engine "gemini".
  Prompt: "Return only JSON with keys <list>. Use null for anything not clearly visible. Never guess."

extract_offline: pdfplumber text of all pages.
  - If text length < 40 chars -> document_quality "scanned", all fields null (this makes scanned PDFs go ON_HOLD).
  - vendor_name: first non-empty line.
  - vendor_tax_id regex: \b(\d{2}[A-Z]{5}\d{4}[A-Z]\dZ\d)\b
  - vendor_bank_account regex: \b([A-Z]{4}0\d{6}-\d{4})\b
  - invoice_number: invoice\s*(?:no\.?|number|#)\s*[:\-]?\s*([A-Z0-9\-\/]+)
  - invoice_date: invoice\s*date\s*[:\-]?\s*(\d{4}-\d{2}-\d{2})
  - due_date: due\s*date\s*[:\-]?\s*(\d{4}-\d{2}-\d{2})
  - po_reference: \b(PO-\d+)\b
  - subtotal: last match of  sub\s*-?\s*total\s*[:\-]?\s*(?:INR)?\s*([\d,]+(?:\.\d+)?)
  - tax_amount: last match of  (?:gst|tax|vat) amount\s*[:\-]?\s*(?:INR)?\s*([\d,]+(?:\.\d+)?)
  - total: last match of  (?<!sub)(?:grand\s+total|total\s+due|amount\s+due|total)\s*[:\-]?\s*(?:INR)?\s*([\d,]+(?:\.\d+)?)
  - field_confidence = 0.9 for each found required field, null otherwise; missing_fields lists the null ones.
  - currency "INR", engine "offline".
  All regexes are case-insensitive. Generated invoices MUST use these exact labels (section 10).

9. API CONTRACT (main.py)
---------------------------------------------------------------------
POST /api/runs                 multipart file upload -> creates run (status RUNNING), starts pipeline in a daemon thread,
                               returns {"id": run_id}
POST /api/runs/sample          json {"name": "01_happy.pdf"} -> copies samples/<name> into uploads and starts a run
GET  /api/samples              list of sample file names
GET  /api/runs                 list of runs (id, filename, status, reason_codes, po_number, amount, created_at), newest first
GET  /api/runs/{id}            {"run": {...full row...}, "events": [...]}
GET  /api/runs/{id}/events     ?after=<event_id> -> events with id > after (used for live polling, every 400 ms)
GET  /api/runs/{id}/file       serves the uploaded PDF (for the preview iframe)
POST /api/runs/{id}/action     json {"action": "approve"|"reject"|"request_info", "note": ""}
                               only for NEEDS_REVIEW or ON_HOLD runs; updates status (APPROVED / REJECTED / ON_HOLD),
                               on approve adds amount to pos.billed, and logs an event stage "human_review"
GET  /api/pos                  PO ledger rows with remaining = total - billed
GET  /api/vendors              vendor master
GET  /api/policy               policy table + assumptions list
GET  /api/stats                {total, by_status, approved_value, stp_rate, avg_ms}
POST /api/reset                delete runs and events, re-run seed.run() (resets PO billed amounts)
Static files mounted at "/" (app/static, html=True). On startup: db.init(); seed.run() if vendors table is empty.

Live updates use POLLING of /api/runs/{id}/events (not SSE) to avoid thread/async bugs.

11. EDGE CASES (the four we showcase, plus one bonus)
---------------------------------------------------------------------
EC1  SPLIT BILLING AGAINST ONE PO (files 02, 03)
     A vendor splits one PO into several invoices. We match on cumulative billed vs remaining balance, not invoice
     total vs PO total. Invoice 2 is approved and the ledger updates; the next oversized invoice is rejected as over-billing.
     Shows: state across runs (PO ledger tab).

EC2  NEAR-DUPLICATE RESUBMISSION (files 04, 05)
     Exact file duplicate is rejected automatically. A corrected/resent invoice ("INV2231 (Revised)") that normalizes to the
     same invoice number is sent to a human with a side-by-side comparison instead of auto-rejecting.
     Shows: balance between preventing double payment and not blocking legitimate corrected invoices.

EC3  SCANNED / UNREADABLE INVOICE WITH MISSING KEY DATA (file 06)
     Extraction confidence gate fails. The system does not guess; status ON_HOLD with a drafted email naming exactly which fields
     were unreadable.
     Shows: graceful degradation, human in the loop with a specific ask.

EC4  TAX EMBEDDED VS SEPARATED / PO BASIS (file 07)
     PO is net 200000; invoice total is 236000 including GST. Naive comparison flags 18% over-billing. We normalize to the PO's
     basis (net) and approve; the reasoning shows the normalization.
     Shows: domain understanding of messy invoice formats.

BONUS  BANK DETAILS CHANGED (file 10)
     Invoice bank account differs from the vendor master -> NEEDS_REVIEW with a fraud warning. Cheap to build, high impact.

Known tradeoff to mention in the demo: the fuzzy duplicate rule (same vendor, same amount, dates within 7 days) can flag
legitimate repeat invoices; the cost is a human review, not a wrong rejection.

17. INTERVIEW TALKING POINTS
---------------------------------------------------------------------
1. Why the LLM only extracts and rules decide: auditability, determinism, cost of a wrong payment.
2. Hallucination control: null instead of guess, confidence gate, deterministic recomputation, offline fallback.
3. Tax/basis normalization and why a naive total comparison creates false mismatches.
4. Why fuzzy duplicates go to review instead of auto-reject.
5. Scaling to thousands of invoices: job queue, batch extraction, per-vendor templates, real database, ERP integration.
6. Learning loop: reviewer overrides become labeled examples and tolerance suggestions.
7. Biggest assumptions and how to extend them: two-way match, single currency.
